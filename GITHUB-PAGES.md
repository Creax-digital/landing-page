# Публикация новой версии CREAX.digital на GitHub Pages

Подготовлено для репозитория `Creax-digital/landing-page` и существующего домена `creax.digital`.
Сборка рассчитана на корень собственного домена, а не на путь `/landing-page/`.

## Что публиковать

Рекомендуемый вариант: **исходники в GitHub → автоматическая проверка и сборка → GitHub Pages**.

- Архив `creax-github-source-2026-09-11.zip` — исходники для репозитория, включая скрытую папку `.github` с автоматической публикацией.
- Архив `creax-github-static-2026-09-11.zip` — уже собранные публичные файлы. Это резервный вариант для обычного статического хостинга или отдельной ветки публикации, не исходники приложения.

Не смешивайте содержимое двух архивов. В основном сценарии используется первый. Исходники не содержат историю Git или настройки частного проекта Sites.

## Безопасная замена старой версии

1. В существующем репозитории сохраните старую версию: **Code → Download ZIP** и отдельно запишите текущий commit из истории. Сделайте снимок **Settings → Pages**: источник публикации, домен, HTTPS. При желании создайте резервную ветку от текущего `main`.
2. Клонируйте именно существующий репозиторий через GitHub Desktop. Создайте ветку, например `codex/static-publication`. Не создавайте новый репозиторий и не удаляйте его историю.
3. Распакуйте архив исходников и скопируйте его содержимое в корень клонированного проекта — без лишней внешней папки. Сохраните существующую папку `.git`. Обязательно перенесите `.github` и `.gitignore`; в Finder скрытые файлы показываются сочетанием **⌘⇧.**.
4. Просмотрите изменения в GitHub Desktop. Старые `index.html`, `robots.txt`, `sitemap.xml` и старые медиа в корне больше не являются источником новой сборки. Их можно удалить из новой ветки после резервного копирования; не удаляйте вслепую другие файлы репозитория. Старый корневой `CNAME` допустимо оставить, если в нём только `creax.digital`: новый артефакт получает свой `CNAME` из `public/CNAME`. Если есть файлы подтверждения поисковых сервисов, перенесите их в `public/` и добавьте в список `publicAssets` сборщика.
5. Сделайте commit, отправьте ветку и откройте pull request в `main`. Дождитесь зелёной проверки **Check and publish GitHub Pages / build**. Pull request только проверяется — сайт на домене не заменяется.
6. Когда готовы к переключению, в **Settings → Pages → Build and deployment → Source** выберите **GitHub Actions**. Сохраните **Custom domain: creax.digital** и **Enforce HTTPS**. Затем объедините проверенный pull request в `main`. Не выбирайте публикацию исходников из корня ветки: там нет готового сайта.
7. В разделе **Actions** дождитесь успешных заданий `build` и `deploy`. Если объединение произошло до настройки Pages и публикация не прошла, после исправления настроек запустите этот workflow вручную через **Run workflow** на `main`.
8. Откройте https://creax.digital/ в приватном окне и пройдите проверки ниже. Исходники можно обновлять дальше обычными commit/push: сборка будет автоматической.

При сохранении текущего репозитория и домена перенос DNS на другой сервер не нужен. **Записи REG.RU, почтовые MX/TXT и настройки домена не меняйте**, если GitHub уже успешно обслуживает этот домен. Если проверка домена в Pages показывает ошибку, сначала выясните её причину; эта подготовка не проверяет и не изменяет ваш аккаунт REG.RU.

Workflow использует стандартный временный токен GitHub. Личный токен, пароль GitHub и ключи от REG.RU добавлять в сайт не требуется. Доступ на публикацию ограничен отдельным заданием `deploy`; pull request не получает этих прав.

## Проверка после публикации

- Главные страницы: `/ru/`, `/en/`, `/zh-hans/`.
- Прямое открытие и перезагрузка `/ru/creative/`, `/ru/products/`, `/ru/systems/`, `/ru/work/`.
- Переключение языка сохраняет раздел; русская ссылка остаётся русской независимо от страны посетителя.
- `/robots.txt` и `/sitemap.xml` открываются; в карте сайта только адреса `https://creax.digital/`.
- Несуществующий путь, например `/check-missing-page/`, показывает страницу 404 и возвращает HTTP 404, а не копию главной с HTTP 200.
- Изображения, меню на телефоне, анимации, Telegram и email работают. В режиме уменьшения движения анимации не мешают чтению.
- В исходном HTML страницы, даже без выполнения JavaScript, есть заголовок, описание, тексты услуг, ссылки и разметка Schema.org.

Локальные тесты проверяют обычную файловую модель хостинга. Окончательно подтвердить ответы GitHub, HTTPS и доступность из целевых стран можно только после публикации.

## Индексация и AI-поиск

После успешной публикации подтвердите владение доменом в Google Search Console, Яндекс Вебмастере и Bing Webmaster Tools. Если домен уже подтверждён, не создавайте новые дублирующие ресурсы. Отправьте карту сайта:

https://creax.digital/sitemap.xml

Проверьте главную и по одной странице каждого направления инструментом проверки URL. Для китайского рынка отдельно оценивайте доступность из материкового Китая и требования нужных поисковых систем; сам перевод не гарантирует индексацию в Baidu.

Подготовленная техническая основа:

- Полный HTML, стабильные адреса, обычные ссылки, HTTP-совместимая структура каталогов.
- Уникальные заголовки и описания; canonical и взаимные hreflang для трёх языков.
- Реальные HTML-атрибуты `lang`, адаптивные изображения, размеры изображений и облегчённые иконки.
- Связанные сущности Organization, WebSite, WebPage/CollectionPage и Service. Без вымышленных рейтингов, адресов или клиентских результатов.
- Открытый `robots.txt`, XML-карта сайта, индексируемые страницы и `noindex` для 404.

`llms.txt` — лишь дополнительный указатель на содержательные страницы. Он не является стандартной заявкой в AI-выдачу: Google прямо указывает, что не использует этот файл для своих генеративных функций. Никакой тег не гарантирует ни индексацию, ни цитирование нейросетью. Основа — полезная информация и доступность сайта. [Рекомендации Google по AI-поиску](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide).

Для дальнейшего роста полезнее дополнять сайт реальными разборами проектов: задача, ограничения, подход, результат, конкретные демонстрации. Перед публикацией подтвердите достоверность существующих кейсов и право на показ материалов. Если это концепты, обозначьте их как концепты; обезличивание клиента не заменяет фактического опыта. Не добавляйте непроверенные цифры ради SEO.

Системы аналитики, формы с отправкой заявок и интеграция с CRM в этой подготовке не подключаются. Контакты работают через Telegram и email. Секреты CRM и AI-сервисов нельзя помещать в публичный JavaScript; будущая интеграция должна идти через отдельный защищённый API.

## Откат

Если после публикации обнаружена проблема в новой версии, откатите соответствующий commit через **Revert**, отправьте изменение в `main` и дождитесь повторной сборки. Не используйте принудительную перезапись истории.

Для полного возвращения старого сайта можно вернуть прежний источник Pages и резервную ветку со старой статикой согласно сохранённому снимку настроек. Оставьте тот же домен и HTTPS. Если используете иной способ публикации, отключите ненужный workflow, чтобы следующий push не перезаписал результат.

## Для разработчика

```bash
pnpm install --frozen-lockfile
pnpm run check:static
pnpm run preview:static
```

Нужны Node.js 24 и pnpm из `packageManager`. Файл `pnpm-workspace.yaml` разрешает установочные сценарии только закреплённых версий нативных сборочных зависимостей; его также нужно перенести в репозиторий. `dist/github-pages/` — единственный каталог загрузки в Pages. Нельзя публиковать весь проект или `dist/server/`.

Экспорт использует существующий vinext. В текущей beta-версии перенаправления со слешем мешают prerender, а метаданные-функции не выгружаются автоматически. Поэтому `prepare-static.mjs` размещает готовый HTML в каталогах, задаёт `html lang` до запуска JavaScript и сохраняет результаты обработчиков robots/sitemap/manifest в файлы. Исходный код фреймворка не патчится; успешная сборка проверяется тестами.

GitHub Pages не исполняет `.htaccess`, серверные API и настройки собственного Nginx. Заголовками кэширования управляет платформа. Статическая сборка переносима на другой файловый хостинг, но для другого домена нужно обновить реквизиты, CNAME, метаданные и связанные проверки. GitHub Pages имеет [ограничения использования](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits); перед использованием для нового коммерческого функционала сверяйтесь с ними.

Официальная инструкция: [GitHub Pages с GitHub Actions](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).
